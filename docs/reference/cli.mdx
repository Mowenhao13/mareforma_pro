## Overview

```bash
mareforma [COMMAND] [OPTIONS]
```

Available commands: `bootstrap`, `key`, `validator`, `claim`, `status`, `activity`, `export`, `verify`, `map`, `diagnose`, `audit`, `observe`, `measure`, `reexec`, `restore`, `mcp`.

## bootstrap

Generate an Ed25519 signing key for this user. Run once after installing mareforma.

```bash
mareforma bootstrap [OPTIONS]
```

The key is written to `~/.config/mareforma/key` (XDG-compliant) with mode `0600`. After bootstrap, every claim written via `mareforma.open()` is signed with this key and the signature envelope is persisted to the row's `signature_bundle` column.

**Options**

| Option | Default | Description |
|---|---|---|
| `--key-path PATH` | `~/.config/mareforma/key` | Override the default key path |
| `--overwrite` | `False` | Replace an existing key. **Destructive**: strands every claim signed by the prior key (verification breaks) AND every claim not yet submitted to Rekor becomes permanently un-loggable |

Safe rotation: back up the old key, run `graph.refresh_unsigned()` to drain the pending queue, then rotate.

**Examples**

```bash
mareforma bootstrap
# → Generated signing key at /home/you/.config/mareforma/key
# → Public key id: ed25519:abc123...
```

## key

Inspect the locally-configured signing key. A bare `mareforma key` prints the group help and exits 2.

```bash
mareforma key [SUBCOMMAND]
```

### key show

Print the public half of the local signing key. The private key never leaves the file at `--key-path` (default `~/.config/mareforma/key`); what this command emits is the public half, safe to email, paste, or pipe.

```bash
mareforma key show [OPTIONS]
```

**Options**

| Option | Default | Description |
|---|---|---|
| `--key-path PATH` | `~/.config/mareforma/key` | Override the default key path |
| `--pem` | `False` | Emit only the PEM-encoded public key to stdout, for `validator add --pubkey` |
| `--keyid` | `False` | Emit only the keyid (SHA-256 hex of the raw public key bytes), for scripts |

**Examples**

```bash
mareforma key show                     # human-readable identity card
mareforma key show --pem > pubkey.pem  # send to a project admin to be enrolled
mareforma key show --keyid
```

## validator

Manage the per-project validators table: who may sign off on a claim.

```bash
mareforma validator [SUBCOMMAND]
```

The first key opened against a fresh `graph.db` auto-enrolls as the root validator (silent self-signed enrollment, with a `UserWarning` so an operator who opened the project with the wrong key has a chance to notice).

### validator add

Enroll a new validator on the current project. The currently loaded signing key signs the enrollment and becomes the parent of the new validator. The signer must already be enrolled.

```bash
mareforma validator add --pubkey PATH_OR_PEM --identity LABEL [--type human|llm]
```

**Options**

| Option | Description |
|---|---|
| `--pubkey TEXT` | PEM-encoded public key. Pass a file path or paste the PEM text. File reads capped at 64 KB |
| `--identity TEXT` | Display label (email, lab name, etc.). 256-char cap; control characters and Unicode display-spoofing forms are rejected |
| `--type human\|llm` | Self-declared validator type. Default `human`. `llm` validators may sign validation envelopes, and recording one on a claim is refused |

**Examples**

```bash
mareforma validator add --pubkey ./alice.pub.pem --identity alice@lab.example
mareforma validator add --pubkey ./bot.pub.pem --identity reviewer-bot --type llm
```

### validator list

List the project's validators in the order they were added. Each row is
checked against the enrollment chain: a row that does not chain back to the
single self-signed root is marked `UNVERIFIED` (`"verified": false` under
`--json`) and the command exits 1.

```bash
mareforma validator list [OPTIONS]
```

**Options**

| Option | Description |
|---|---|
| `--json` | Emit JSON to stdout |

## claim

Manage scientific claims.

```bash
mareforma claim [SUBCOMMAND]
```

### claim add

Assert a new scientific claim.

```bash
mareforma claim add TEXT [OPTIONS]
```

**Arguments**

| Argument | Description |
|---|---|
| `TEXT` | The claim text. Falsifiable assertion. |

**Options**

| Option | Default | Description |
|---|---|---|
| `--classification` | `INFERRED` | `INFERRED` \| `ANALYTICAL` \| `DERIVED` |
| `--status` | `open` | `open` \| `contested` \| `retracted` |
| `--source TEXT` | none | Data source name |
| `--supports ID_OR_DOI` | none | Upstream claim_id or DOI (repeatable) |
| `--contradicts ID_OR_DOI` | none | Claim_id this finding contests (repeatable) |
| `--generated-by TEXT` | `agent` | Agent identifier |
| `--artifact-hash TEXT` | none | SHA-256 hex digest of the output bytes backing the claim. Bound into the signed payload; converging peers must match when both supply a hash |

**Examples**

```bash
# Basic claim
mareforma claim add "Target T is elevated in condition C"

# With classification, source, and artifact hash
mareforma claim add "Target T is elevated in condition C (n=620)" \
  --classification ANALYTICAL \
  --source dataset_alpha \
  --generated-by "agent/model-a/lab_a" \
  --artifact-hash "$(sha256sum figure_3.png | cut -d' ' -f1)"

# Building on prior findings
mareforma claim add "The mechanism is likely M" \
  --classification DERIVED \
  --supports 3f8a1b2c-...
```

### claim list

List claims, optionally filtered.

```bash
mareforma claim list [OPTIONS]
```

**Options**

| Option | Default | Description |
|---|---|---|
| `--status TEXT` | none | Filter by status: `open`, `contested`, `retracted` |
| `--source TEXT` | none | Filter by source name |
| `--limit INT` | unbounded | Most claims to list. The listing says when a limit capped it. With `--json` that notice goes to stderr and stdout stays a bare JSON array, so a script parsing it is unaffected |

A row whose signature no longer re-verifies still prints, marked `UNVERIFIED`
beside its classification, so an auditor sees it rather than losing it from the

the same marker.

**Examples**

```bash

mareforma claim list --status open
mareforma claim list --json | jq '.[].classification'
```

### claim update

Update editable fields on an existing claim.

```bash
mareforma claim update CLAIM_ID [OPTIONS]
```

**Options**

| Option | Description |
|---|---|
| `--status TEXT` | New status: `open`, `contested`, `retracted` |
| `--text TEXT` | New claim text (rejected on signed claims) |
| `--supports ID_OR_DOI` | Replace supports list (rejected on signed claims) |
| `--contradicts ID_OR_DOI` | Replace contradicts list (rejected on signed claims) |

Signed claims (those with a non-NULL `signature_bundle`) refuse mutation of `text` / `supports` / `contradicts`; these are part of the signed payload and silent mutation would invalidate the signature. To revise a signed claim, retract it (`--status retracted`) and assert a new one citing the old via `--contradicts <old_claim_id>`. `status` remains editable since it is not part of the signed payload.

### claim validate

Record a signed human validation on a claim. Identity-gated, and terminal.

```bash
mareforma claim validate CLAIM_ID [OPTIONS]
```

Requires a loaded signing key (`mareforma bootstrap` first) AND that key must be enrolled in the project's `validators` table. The validation event itself is signed: a DSSE-style envelope binding `(claim_id, validator_keyid, validated_at)` is persisted to the row's `validation_signature` column.

**Options**

| Option | Description |
|---|---|
| `--validated-by TEXT` | Cosmetic display label of the reviewer. The authoritative identity is the keyid embedded in the signed envelope |

**Examples**

```bash
mareforma claim validate abc123
mareforma claim validate abc123 --validated-by reviewer@example.org
```

## status

Show the epistemic health dashboard.

```bash
mareforma status [OPTIONS]
```

**Traffic light**

| Color | Condition |
|---|---|
| 🔴 RED | No claims recorded |
| 🟡 YELLOW | Claims exist but none standing carries a signed validation, or every claim that carried one has been retracted or invalidated by a signed contradiction verdict, or something carrying signed material does not re-verify on read |
| 🟢 GREEN | At least one standing claim carries a signed validation, meaning it is not retracted and not invalidated by a signed contradiction verdict, and everything carrying signed material re-verifies |

The light cannot read green while a claim carrying signed material fails
re-verification: an envelope stapled onto another row, a signed field rewritten
underneath, or a swapped signature. The report names how many, so `mareforma
verify <claim_id>` can find which, to retract or repair.

**Options**

| Option | Description |
|---|---|
| `--json` | Emit JSON to stdout |

## activity

Show rolling operational rates from the activity log (`.mareforma/health.jsonl`), one JSONL line per operation that produces operational signal: provenance queries, grounding sensor verdicts, `refresh_unsigned` retries. The report gives grounding-pass-rate and Rekor-log-recovery-rate, so an operator sees how mareforma has been behaving without re-querying `graph.db`.

Distinct from `mareforma status`: `status` is a snapshot of graph state right now, `activity` is a rolling view of what mareforma has been doing. `mareforma stats` is a deprecated alias for this command.

```bash
mareforma activity [OPTIONS]
```

**Options**

| Option | Default | Description |
|---|---|---|
| `--json` | `False` | Emit JSON to stdout instead of a formatted table |
| `--last N` | all events | Aggregate only the last N events (N >= 1) |

**Examples**

```bash
mareforma activity
mareforma activity --last=100
mareforma activity --json
```

## export

Export all claims as a JSON-LD document, optionally as a signed bundle.

```bash
mareforma export [OPTIONS]
```

**Plain JSON-LD** (`--format=jsonld`, default). Writes `ontology.jsonld` in the mareforma-native vocabulary (`@type=mare:Graph`, media type `application/x-mareforma-graph+json`). This default format is NOT PROV-O-conformant: it uses an honest mareforma-native vocabulary rather than name-dropping PROV-O without populating the full graph. For a real W3C PROV-O graph, use `--format=prov-o` (below). Each claim node carries every `SIGNED_FIELDS` member so a bundle verifier can re-derive `canonical_statement` bytes from a node alone.

**Interop formats** (`--format`). Beyond the native JSON-LD, `export` emits three interchange formats for external tooling:

- `--format=in-toto-v1`: an unsigned in-toto Statement v1 (read by sigstore, SLSA and GUAC tooling). Distinct from `--bundle`, which produces a *signed* in-toto v1 envelope.
- `--format=ro-crate-1.2`: an RO-Crate 1.2 Process Run Crate (`ro-crate-metadata.json`).
- `--format=prov-o`: a W3C PROV-O JSON-LD graph for provenance-aware tooling.

**Signed bundle** (`--bundle`). Wraps the JSON-LD export in an in-toto Statement v1 envelope and signs it with the local Ed25519 bootstrap key, or with the key `--key` pins when the project's root validator is not the default key. The bundle includes one subject entry per claim (`urn:mareforma:claim:<uuid>`) with a SHA-256 of the claim's canonical Statement v1 bytes, plus a bundle-level DSSE signature. `--bundle` and `--format` are mutually exclusive: `--bundle` always signs the native JSON-LD.

**Options**

| Option | Default | Description |
|---|---|---|
| `--format [jsonld\|in-toto-v1\|ro-crate-1.2\|prov-o]` | `jsonld` | Export format. Mutually exclusive with `--bundle` |
| `--output PATH` | `ontology.jsonld` in the project root, not the working directory (varies by `--format`; `mareforma-bundle.json` with `--bundle`) | Output file path |
| `--json` | `False` | Print JSON-LD to stdout instead of writing a file. Mutually exclusive with `--bundle` |
| `--bundle` | `False` | Produce a signed bundle (in-toto Statement v1 + DSSE) |
| `--key FILE` | local bootstrap key | Signing key for `--bundle`. Pin this when the project's root validator is not the default key. Rejected without `--bundle`, since every other export is unsigned |

**Examples**

```bash
# Plain JSON-LD
mareforma export
mareforma export --output /tmp/my_claims.jsonld
mareforma export --json | jq '.["@graph"][] | select(.["@type"] == "mare:Claim")'

# Interop formats
mareforma export --format=in-toto-v1
mareforma export --format=ro-crate-1.2 --output crate-metadata.json
mareforma export --format=prov-o --output mareforma-prov-o.jsonld

# Signed bundle
mareforma export --bundle
mareforma export --bundle --output /tmp/release.bundle.json
```

The JSON-LD output uses `mare:` and `schema:` vocabularies. Each claim is a `mare:Claim` node with `claimText`, `classification`, `claimStatus`, `generatedBy`, `dateCreated`, `supports`, `contradicts`, `sourceName`, and `artifactHash` fields. There is no `supportLevel` term: it carried the retired support ladder, so a consumer keyed on it finds it absent rather than frozen at a value.

## verify

Verify a claim, a signed bundle, a signed audit receipt, or an export directory. An existing directory is read as an export dir and anything that is not an existing path as a claim id resolved against the local project. An existing **file** is routed by its DSSE `payloadType`, never by its name:

| `payloadType` | Verified as |
|---|---|
| `application/vnd.mareforma.audit-receipt+json` | A per-finding audit receipt from `mareforma audit` |
| `application/vnd.mareforma.audit-run+json` | A signed audit run record |
| anything else | A signed bundle |

A signed audit run record is always unverifiable (exit 2), whether or not its signature checks out. Its `completed` flag is the key a `--corpus` audit resumes on, not a claim verdict, so `verify` reports on it and refuses to call it verified or tampered.

For a bundle, this checks the DSSE signature (over the DSSE PAE encoding, so it interoperates with standard verifiers), every per-claim subject digest, every per-claim **asserter signature** bound to the claim's presented content, the enrolled validator chain to a single root (which must be the bundle signer), and every **validation envelope** a node carries against that validator set. For a claim id, verification uses only public material (auditor mode) and prints the claim's trust map.

Auditor mode verifies against enrolled validator pubkeys only, so a signed claim whose signer is **not an enrolled validator** cannot be authenticated: the claim's binding is all that could be checked, never its signature. `verify` exits **2** on such a claim, not 0. Exit 2 is the unverifiable verdict, not a failure: enrol the signer's key and run it again to reach one. A CI gate built on `verify` therefore no longer passes a claim carrying an all-zero signature under a keyid that was never enrolled, and a gate that treats 2 as a failure will stop a claim that may be perfectly sound. Route 2 to "cannot tell yet", and reserve 1 for a definite failure.

Editorial status (`retracted` / `contested`) and comparison summaries carry no signature in the data model, so a verified bundle does not attest them: it attests each claim's asserter content and the validation envelopes that claim carries, not a mutable status flag.

```bash
mareforma verify TARGET [OPTIONS]
```

**Arguments**

| Argument | Description |
|---|---|
| `TARGET` | A claim id, a signed file (bundle, audit receipt, or audit run record), or an export directory. An existing dir → export dir, a path that does not exist → claim id, an existing file → routed by its DSSE `payloadType` |

**Options**

| Option | Description |
|---|---|
| `--json` | Emit a machine-readable verdict (and, for a claim, its trust map) to stdout |
| `--redact-home` | Rewrite `$HOME` to `~` in the printed trust map (never applied to signed receipts) |
| `--key FILE` | Signer key to verify a bundle, export directory, or audit receipt against (defaults to the local bootstrap key). Pin this when the signer is not the default key. A receipt signed with a non-default key that is *not* pinned reads as unverifiable (exit 2), not tampered; once pinned, a mismatch is a definite failure (exit 1) |

**Exit codes** (stable, for CI gates). The 1-vs-2 split is the point: a gate must tell "this claim is tampered" from "I could not check this claim."

| Code | Meaning |
|---|---|
| `0` | verified |
| `1` | tamper or binding violation (a definite NO) |
| `2` | unverifiable (missing material to reach a verdict, not a NO) |
| `3` | usage error (bad flag or argument) |

**Examples**

```bash
mareforma verify <claim-id>
mareforma verify <claim-id> --json
mareforma export --bundle
mareforma verify mareforma-bundle.json
# → Bundle verified: 12 claim subject(s) match.
mareforma verify ./export-dir

mareforma audit --key auditor.key --findings findings.json --out audit/ -- python analysis.py
mareforma verify audit/envelopes/001-f1.json --key auditor.key
```

## diagnose

Run a Python target under the observer and report what data flowed. `COMMAND` runs in-process (via `runpy`, the coverage.py pattern; a subprocess would hide the target behind the observer's own seam) with the grounding observer active, then the observed reads, seams, and coverage are printed. With `--cites` the grounding verdict for those sources is computed too; without it the report is observation-only, because no verdict is invented for a citation you did not state.

A target that crashes still prints its partial observation and exits with the target's own exit code. `COMMAND` is a script path, a script path behind `python`, or `-m module`. Interpreter flags (`-u`, `-O`, `-X`, ...) are rejected: the target runs in-process, so there is no interpreter to pass them to.

A target with a non-Python file extension is refused as a usage error, **exit 3**, before anything runs. 3 rather than 2 because `diagnose` and `audit` exit with the target's own exit code, and 2 is one of the commonest codes a script exits with (argparse uses it for its own usage errors), so a gate reading 2 could not tell "you passed a non-Python target" from "your script rejected its arguments". 3 is the same usage-error code `verify` and `reexec` use. A version marker is not a file extension: `pipeline.v2` and `model.v1.2` run. A JSON run spec handed to the wrong flag is a valid Python dict literal: it compiles, exits cleanly, reads nothing, and the report would say `UNGROUNDED` with `scope fully observed` beside it, which is a false accusation carrying a false completeness claim. Everything `runpy` can run is accepted: `.py`, `.pyw`, `.pyz`, `.pyc`, `.zip`, a directory or zipapp with a `__main__`, an extensionless script, and `-m module`. `audit` applies the same rule, because both commands make the same promise about what they watched.

```bash
mareforma diagnose [OPTIONS] COMMAND...
```

**Options**

| Option | Default | Description |
|---|---|---|
| `--cites SRC` | none | A source the run should ground on (path, URL, or `sha256:`). Repeatable |
| `--json` | `False` | Emit the observation report as JSON |
| `--redact-home` | `False` | Rewrite `$HOME` to `~` in the emitted report |

**Examples**

```bash
mareforma diagnose -- python analysis.py
mareforma diagnose --cites /data/trial.csv -- analysis.py
mareforma diagnose -- -m mypkg.pipeline
```

## audit

Audit a third-party pipeline: one signed grounding receipt per finding. Runs `COMMAND` in-process under the grounding observer, exactly like `diagnose`; the target never imports mareforma. The findings mapping names what each finding claims to cite, the observer alone supplies what happened, and nothing the target prints or writes enters a verdict. Each finding gets a verdict receipt (`receipts.jsonl` feeds `mareforma measure`) plus a signed envelope `mareforma verify` checks from public material alone. `audit` exits with the target's own exit code; a crashing target still emits its partial receipts.

The target shares the auditor's interpreter (in-process observation is what makes its reads visible), so the receipts grade a pipeline that does not attack its auditor: a target written to defeat the audit could fabricate what the observer records. The signature attests the auditor's observation, not the target's honesty.

With `--corpus`, `audit` iterates run specs instead: one fresh interpreter per run, resumable (a run whose signed record verifies as complete is skipped on re-invocation).

```bash
mareforma audit [OPTIONS] [COMMAND]...
```

**Options**

| Option | Default | Description |
|---|---|---|
| `--findings FILE` | none | JSON object mapping `finding_id` to its cited source(s). Required unless `--corpus` is given |
| `--corpus DIR` | none | Directory of run specs (`*.json`, each carrying `command` and `findings`). Resumable; one fresh interpreter per run |
| `--out DIR` | `mareforma-audit` | Output directory for the run record, receipts, and signed envelopes |
| `--key FILE` | bootstrap key | Auditor signing key |
| `--json` | `False` | Emit the run record as JSON |
| `--redact-home` | `False` | Rewrite `$HOME` to `~` in the printed report (never applied to signed receipts) |

**Examples**

```bash
mareforma audit --findings findings.json -- python analysis.py
mareforma audit --findings findings.json --out audit/ -- -m mypkg.run
mareforma audit --corpus runs/ --out audit/
```

## measure

Aggregate a pipeline's grounding verdicts into the reported split. `RECEIPTS_PATH` is required (a bare `mareforma measure` exits 2 with `Error: Missing argument 'RECEIPTS_PATH'.`) and holds either a JSON array of verdict receipts or a JSONL file with one receipt per line, as `mareforma audit` writes.

The report gives the GROUNDED / UNGROUNDED / OPAQUE split, the incidental-read rate, mean read coverage, and OPAQUE bucketed by seam kind. When a receipt carries an `independence` record, the independence arm is reported alongside it: the effective-independence distribution, the UNVERIFIABLE fraction, and the same-model-collapse rate.

When a receipt carries an `influence` record, the influence arm is reported too: for each cited source, whether the finding depends on the data (INFLUENCED / NOT_INFLUENCED / UNDECIDABLE) or was never tested (NOT_TESTED). The unit is the edge, a finding-and-source pair, so one finding that cites several sources contributes several edges. The rate denominator is the edges the oracle DECIDED, INFLUENCED plus NOT_INFLUENCED: an UNDECIDABLE edge is the oracle saying it could not call that one, and NOT_TESTED means nothing ran, so both are counted, named in the summary line and left out of the rate. A rate prints the number of distinct runs behind it, or says the writer recorded none. The `NOT_TESTED by reason` buckets are the typed `NotTestedReason` values plus `not-run` (NOT_TESTED with no typed reason, which is what `mareforma audit` writes) and `unknown` (a malformed or unrecognised record). The `mareforma audit` path observes flow with a single run and does not perturb, so on its receipts every edge reads NOT_TESTED: the report says influence was not tested rather than letting a grounding verdict stand in for an influence claim nobody measured.

```bash
mareforma measure RECEIPTS_PATH [OPTIONS]
```

**Arguments**

| Argument | Description |
|---|---|
| `RECEIPTS_PATH` | JSON array of verdict receipts, or a JSONL file with one receipt per line |

**Options**

| Option | Default | Description |
|---|---|---|
| `--json` | `False` | Emit the report as JSON |
| `--redact-home` | `False` | Rewrite `$HOME` to `~` in emitted paths (never applied to signed receipts) |

**Examples**

```bash
mareforma measure run-receipts.jsonl
mareforma measure run-receipts.json --json --redact-home
```

## reexec

Re-run a recorded pipeline and check the reported number reproduces. `RUN_PATH` is a JSON run record: the recorded `reported_value`, a pipeline naming a `module:attr` entry point (plus optional args), a declared `tolerance` and `rel_tolerance`, and, when the run cannot be re-run faithfully, `"reexecutable": false` with a `not_reexecutable_reason` (`world_contact`, `private_data`, or `expensive_compute`).

The verdict is three-valued and honest: REPRODUCED (re-ran and matched), DIVERGED (re-ran and differed), or COULD_NOT_REEXECUTE (could not run, so faithfulness is unknown, never a false REPRODUCED). It attests reproducibility, not correctness, and a same-arm re-run is not independence.

With `--map CLAIM_ID` it re-renders that claim's trust map with the verdict placed on the faithfulness axis, so the proxy is read next to every other trust property. The verdict is not stored; it is a read-side overlay.

```bash
mareforma reexec RUN_PATH [OPTIONS]
```

**Arguments**

| Argument | Description |
|---|---|
| `RUN_PATH` | JSON run record naming the recorded value, the `module:attr` entry point, and the declared tolerance |

**Options**

| Option | Description |
|---|---|
| `--json` | Emit the verdict as JSON |
| `--map CLAIM_ID` | Also render `CLAIM_ID`'s trust map with the faithfulness verdict placed on its PROXY-tier axis |

**Exit codes** (stable, for CI gates). The verdict carries in the exit code, with malformed input distinct from an honest inconclusive re-run.

| Code | Meaning |
|---|---|
| `0` | REPRODUCED |
| `1` | DIVERGED |
| `2` | COULD_NOT_REEXECUTE (faithfulness unknown, not a NO) |
| `3` | usage error (bad flag or argument, malformed run record, or an unrenderable `--map`) |

**Examples**

```bash
mareforma reexec run.json
mareforma reexec run.json --json
mareforma reexec run.json --map <claim-id>
```

## restore

Rebuild `graph.db` from `claims.toml` for catastrophic-loss recovery. Refuses to run if the project's `graph.db` already contains claims: fresh-only, not merge. Every signature is verified before any row is inserted; fail-all-or-nothing.

```bash
mareforma restore [CLAIMS_TOML_PATH]
```

**Arguments**

| Argument | Description |
|---|---|
| `CLAIMS_TOML_PATH` | Optional. Path to the source TOML. Defaults to `./claims.toml`. |

**Options**

| Option | Description |
|---|---|
| `--trust-unaccounted-backup` | Restore a backup whose completeness table does not match what the file holds. For a file you edited on purpose: without it, such a file is refused. |

**Examples**

```bash
# Standard case, claims.toml in the project root:
mareforma restore

# Explicit source (e.g. recovered from a backup):
mareforma restore backups/state.toml

# A file you repaired by hand, which no longer matches its own row counts:
mareforma restore --trust-unaccounted-backup
```

The output reports `validators_restored` and `claims_restored` counts. Failure exits `1` with a `RestoreError` message naming the failure mode: `graph_not_empty`, `toml_not_found`, `toml_unreadable`, `toml_malformed`, `enrollment_unverified`, `claim_unverified`, `trust_row_rejected`, `mode_inconsistent`, `orphan_signer`, `policy_violation`, `rekor_inclusion_invalid`, `backup_unaccounted`, `format_ahead`, `verdict_chain_broken`, `verdict_chain_cut_short`, or
`grounding_unattested`. Three further modes (`policy_unverified`, `policy_absent`, `policy_unverifiable`) exist but fire only under `enforce_rekor_policy`, which the CLI `restore` does not expose; see the `mareforma.restore()` API table for those.

`claims.toml` includes a `[rekor_inclusions]` section. Older files written without it restore successfully with a `RekorSidecarSectionAbsentWarning`. Run `refresh_unsigned()` afterward to re-fetch inclusion proofs.

## mcp

Serve one project to an agent over the Model Context Protocol.

```bash
mareforma mcp [SUBCOMMAND]
```

The server is **read and verify only**. It exposes tools that query the graph and check a claim's signatures and grounding-to-citation binding, and it exposes no write path. An agent can look a claim up and audit it across the transport, but cannot assert one: a claim written over the boundary would carry no observed grounding, and the record exists to hold claims to the grounding they earned. The refusal is a designed bound, not a missing feature.

### mcp serve

Run the read-and-verify server on the chosen transport.

```bash
mareforma mcp serve [OPTIONS]
```

The project root is fixed for the process lifetime, resolved once at startup and never per request: a per-request path would be both non-deterministic and a directory-traversal surface. Resolution order is `--project-root`, then the `MAREFORMA_PROJECT_ROOT` environment variable, then discovery from the current directory (the first ancestor holding a `.mareforma/graph.db`).

The project has to be **writable**, and the server refuses to start if it is not. It signs nothing and writes no claims, but SQLite opens the graph read-write and journals beside it even on a pure read. Serve from a copy if the original must stay untouched.

**Options**

| Option | Default | Description |
|---|---|---|
| `--project-root PATH` | discovery | Project to serve. Falls back to `$MAREFORMA_PROJECT_ROOT`, then to discovery from the current directory. Resolved once at startup, never per request |
| `--max-evidence-lines INT` | `1000` | Most evidence lines the three single-id tools will derive over before refusing. Cost is linear in this count and every bit of it holds the one graph lock, so an unbounded derivation on a server costs every other caller their turn |
| `--transport [stdio]` | `stdio` | Transport the server speaks. `stdio` is the Model Context Protocol default |

Above the ceiling, `proposition_status` and `trust_map` return `found: true` with
the derivation left out and a `refused` string saying why: the subject exists,
the server declined to derive it, and answering `found: false` would tell an
agent it is absent. `verify_claim` still returns its verdict, because signature
and binding work does not grow with the evidence, and reports the missing map as
`trust_map_refused`.

**Tools**

| Tool | Answers |
|---|---|
| `query_claims` | Claims matching a text substring and classification |
| `search_claims` | Full-text search, ranked by relevance |
| `get_claim` | One claim by id. `found: false` rather than an error when the id is unknown |
| `proposition_status` | `{found, status}` for a content id. `status` is the whole derived view: `status`, `question_status`, `independent_support`, `independent_refute`, `lines_skipped`, `post_hoc`, `status_policy`. `null` when nothing resolves to that id |
| `trust_map` | A claim's trust map: who signed it, what backs it |
| `verify_claim` | `verified`, `tampered`, or `unverifiable`, by the rule `mareforma verify` applies |

`query_claims` and `search_claims` serve at most 200 rows, 20 by default. Every page carries `count`, the `limit` actually served, and `has_more`: a short page is never mistaken for the whole record, whether it was shortened by the cap or by the default. A `limit` that was not honoured (above the cap, below one row, or not a number) comes back as `limit_requested` rather than being silently swapped. A page that held rows back also says how many, as `verify_excluded`: rows whose signature did not re-verify, which the enumerating tools will not return. `get_claim` still returns such a row with its stored text and no verification signal, so run `verify_claim` on any id you reached that way. An empty list is never read as an empty record.

Claim text comes back sanitized and wrapped in `<untrusted_data>` markers, and the server says so in its instructions. Treat everything between those markers as data written by whoever produced the claim, never as instructions. One consequence: the signature fields in that view are cleaned text rather than the signed bytes, so they are not the material to re-verify from. Use `verify_claim`, which reads the raw row.

**Examples**

```bash
# Serve the project discovered from the current directory:
mareforma mcp serve

# Serve an explicit project, pinned for the process lifetime:
mareforma mcp serve --project-root /path/to/project
```

## mareforma-pro

The optional rootless CLI has two transports. The default `run` path requires
`strace` and a non-setuid `bwrap`. The alternate `run-fuse` path requires
`/dev/fuse`, `fusermount3`, and `bwrap`, and uses no ptrace. Neither requires
`sudo`, CAP_BPF, cgroups, or Tetragon.

```bash
uv add mareforma-pro
```

The distribution is `mareforma-pro` and the import package is
`mareforma_pro`; it depends on and is released independently from core
`mareforma`. The `otel` extra belongs to this distribution:

```bash
uv add "mareforma-pro[otel]"
```

### mareforma-pro doctor

```bash
mareforma-pro doctor --json
```

Reports `strace`, `bwrap`, Yama `ptrace_scope`, `/dev/fuse`, `fusermount3`, and
a real `strace --seccomp-bpf -f` probe. A failed required check exits non-zero;
the P2 FUSE probes are informational and do not fail a P1 host. This is a
host-prerequisite check, not proof that a target's reads are trustworthy.

### mareforma-pro run

```bash
mareforma-pro run \
  --secret "$MAREFORMA_HMAC_SECRET" \
  --cite /data/exp42/results.csv \
  --ro-bind /data/exp42:/tmp/work \
  -- /bin/cat /tmp/work/results.csv
```

Runs the command under `strace --seccomp-bpf -f -y`, parses successful reads
separately from read-opens, signs a `mareforma_pro.rootless_receipt/v1` receipt,
and prints the matching Mareforma grounding record. A cited file opened but not
read is `OPAQUE(open_only)`; an unmapped temporary mount is
`OPAQUE(unmapped_tmpfs)`; a rejected HMAC receipt is
`OPAQUE(unsigned_declared)`. `--source-requirement not_applicable` labels a pure
computation as `OPAQUE(computed_no_external_source)`; it remains OPAQUE and
does not manufacture a data source.

### mareforma-pro serve

```bash
mareforma-pro serve --socket /tmp/mareforma-collector.sock \
  --secret "$MAREFORMA_HMAC_SECRET" --token "$MAREFORMA_COLLECTOR_TOKEN" \
  --db /tmp/mareforma-receipts.sqlite \
  --otel-jsonl /tmp/mareforma-spans.jsonl
```

Starts the local JSON-line Unix-socket collector. Operations are
`open_scope`, `ingest_strace`, `ingest_events`, and `close_scope`. The socket is
created `0600` and rejects a peer with a different Linux UID via `SO_PEERCRED`
(pass `require_same_uid=False` in the Python API only when that boundary is
intentional). The optional token is a second check. The HMAC secret stays in the
parent/collector; target commands are launched with `bwrap --clearenv` by
default. `--otel-jsonl` is optional; it emits non-authoritative scope/process
spans on `close_scope`, and an export failure never changes a receipt.

### mareforma-pro run-fuse

```bash
mareforma-pro run-fuse \
  --secret "$MAREFORMA_HMAC_SECRET" \
  --source /data/exp42 \
  --cite /data/exp42/results.csv \
  -- /bin/cat /tmp/mareforma-data/results.csv
```

Runs the command under a scope-specific, read-only FUSE view of `--source`,
then binds that view into `bwrap` at `--sandbox-path` (default
`/tmp/mareforma-data`). The direct host source path is shadowed by a tmpfs by
default, so the FUSE view is the only route to the data inside the sandbox;
pass `--keep-source-visible` only for debugging. The receipt says
`collector_mode=fuse_read_proxy`, `evidence_level=USER_FUSE`, and
`read_semantics=READ_BYTES`. A successful non-empty FUSE read grounds a cited
host path; an open without a read is `OPAQUE(open_only)`. Because the receipt
also signs `coverage_roots`, a citation outside `--source` is
`OPAQUE(unmapped_sandbox_path)` rather than a confident `UNGROUNDED`. A URL
citation in a FUSE or generic Python/MCP scope with no explicit application URL
manifest is `OPAQUE(trace_incomplete)`, because a FUSE coverage root describes
files, not network delivery. `--source-requirement not_applicable` is available
for a pure-computation run.

`fusermount3` is a setuid system helper used only to obtain the unprivileged
mount. It does not grant the target root, and no `sudo` prompt is involved.

### mareforma-pro supervise

```bash
mareforma-pro supervise \
  --port 18100 \
  --internal-port 18000 \
  --workers 1 \
  --egress-proxy \
  --db-hook \
  -- /path/to/server-venv/bin/python /path/to/mcp_server.py
```

`supervise` is the 0.4.0+ long-running path for an unchanged HTTP MCP server. It
listens on public port `18100` by default and starts the original command on
its fixed internal loopback port `18000`. MCP clients connect to the
supervisor on `18100`; do not connect directly to the internal server. The
server command may use `{external_port}` or `{internal_port}` placeholders, or
the common `--port <public-port>` form is rewritten automatically. `PORT`,
`MCP_PORT`, `UVICORN_PORT`, and `MCP_SERVER_PORT` are set to the internal port,
and the matching `HOST` / `MCP_HOST` / `UVICORN_HOST` / `MCP_SERVER_HOST`
variables are set to loopback for environment-driven servers.

When the server hard-codes `18000`, leave its command unchanged and use
`--workers 1`; only one process can bind that fixed port. To run multiple
workers, point the server at `{internal_port}` (or rewrite it with
`--internal-port`) and give each worker a distinct port.

To keep the remote endpoint unchanged, use the same port on distinct bind
addresses. The child stays on `127.0.0.1:18000`; the Supervisor binds the
concrete address that remote clients already use:

```bash
mareforma-pro supervise \
  --host 10.12.112.230 --port 18000 \
  --internal-port 18000 \
  --workers 1 --egress-proxy --db-hook \
  -- /path/to/server-venv/bin/python /path/to/mcp_server.py
```

Remote clients can keep using `http://10.12.112.230:18000`. The public and
internal ports may match only when their bind hosts differ; a wildcard public
bind such as `0.0.0.0` is refused. Clients that connect through loopback hit
the child directly and bypass the receipt boundary.

For a Python server that hard-codes `0.0.0.0:18000` and must keep the wildcard
endpoint, use runtime bind redirection:

```bash
mareforma-pro supervise \
  --host 0.0.0.0 --port 18000 \
  --internal-port 18100 \
  --bind-rewrite-port 18000 \
  --workers 1 --egress-proxy --db-hook \
  -- /path/to/server-venv/bin/python /path/to/mcp_server.py
```

`--bind-rewrite-port` prepends the Python autohook and redirects only an IPv4
`bind()` matching that exact port to the internal loopback endpoint. The hook
does not cover a non-Python server or a Python process started with `-S`.

A server that imports a large catalog can take longer than the default 30-second
ready timeout. Pass `--ready-timeout 240` or higher and allow the same margin in
the surrounding service manager. The supervisor does not declare the public
port ready until the internal process accepts a TCP connection.

Each POST request gets an HMAC-signed `CallReceipt` in the receipt journal
(`~/.mareforma/mcp-receipts.jsonl` by default); idle sessions and shutdown get
a `SessionReceipt`. Use `--otel-jsonl` for non-authoritative call/session span
events. `--no-strace` is a diagnostic mode and always leaves
`OPAQUE(trace_incomplete)` because no process evidence was captured.

The official MCP Streamable HTTP client opens a long-lived `GET /mcp` SSE
stream after `notifications/initialized` and sends `DELETE /mcp` when the
session closes. The supervisor forwards `GET` and `DELETE` without reserving
the serialized call worker. This keeps standard SDK clients working while
preserving the one-call-at-a-time evidence boundary for POST requests. If a
POST overlaps a live GET, its receipt carries
`OPAQUE(concurrent_call_overlap)` instead of claiming exclusive process
attribution.

`--db-hook` prepends the package's `sitecustomize.py` to `PYTHONPATH` and hooks
SQLite queries plus common Python HTTP clients. It is optional and does not
cover arbitrary native DB drivers. `--egress-proxy` injects
`HTTP_PROXY`/`HTTPS_PROXY`; plain HTTP URLs are visible, while HTTPS reports
the CONNECT authority and `OPAQUE(https_path_opaque)` unless the deployment
adds a trusted local MITM CA. Direct external connections are reconciled
against `strace connect()` and become `egress_proxy_bypassed` or
`egress_uninspected` when the proxy is bypassed or disabled.

### mareforma-pro worker supervise

```bash
mareforma-pro worker supervise \
  --worker-id 1 \
  --receipt-log ~/.mareforma/worker-1-receipts.jsonl \
  --coverage-root /srv/biomni/tasks \
  -- /path/to/worker-venv/bin/python /path/to/worker.py --worker-id 1
```

`worker supervise` is the 0.5.0+ path for a long-running task worker. It starts
an unchanged worker under `strace --seccomp-bpf -f -ttt -yy`, prepends the Python
autohook to `PYTHONPATH`, and signs one task-scoped
`mareforma_pro.rootless_receipt/v1` receipt when `BIOMNI_TASK_ID` transitions.
`BIOMNI_EXECUTION_ID` and the basename of `BIOMNI_ATTEMPT_DIR` become the
receipt's `execution_id` and `attempt`. `-ttt` timestamps are checked against
the task boundaries, so a late FIFO line is charged to the task active when the
syscall completed rather than the next task. The observer must launch the
worker; it cannot attach to a running process without `sudo`.

The receipt adds `task_id`, `worker_id`, `execution_id`, `attempt`, and
`read_bytes`. Its `observed_http` rows carry the credential-free URL, method,
status, response-body length, response SHA-256, and a query digest plus key
names for `urllib`, `requests`, and `httpx`. `observed_db_queries` covers
`sqlite3`, `psycopg`, `psycopg2`, and `redis`; SQL text is recorded by default
and can be disabled with `--no-db-query-text`. Query values in URLs are omitted
unless `--http-query-text` is explicitly set, because presigned URLs often
contain secrets. An unconsumed stream or an unobservable body adds
`OPAQUE(http_body_unobserved)`.

`--no-strace` is diagnostic only and always adds
`OPAQUE(trace_incomplete)`. The worker receipt is not yet cryptographically
bound to a parent MCP request scope: `task_id` / `request_id` / `execution_id`
correlation is not a signed parent-child link. Native reads that bypass both
the Python hook and the strace filter (`mmap`, `io_uring`, direct syscalls) and
direct use of unpatched HTTP transports remain outside the claim.
