你的判断非常准确。把这 4 块能力收口在 `mareforma-pro` 侧、而不是侵入 MCP-server 源码，是从“单任务观测库”迈向“通用 Agent 执行观测框架”的关键一步。

从 0.2.0 演进到下一个版本，核心改动方向是：**在 `mareforma-pro` 中将执行托管层拆分为“短任务一次性运行器（`RootlessBwrapRunner`）”与“长驻服务监督器（`MCPProcessSupervisor`）”双轨架构**，同时把现有的 `MCPApplicationMiddleware` 重新定位为**逻辑边界信号源**，与底层 3 条物理取证通道共同汇入同一个确定性收据管线。

## 一、核心范式切换：从“一次性 Runner”到“长驻 Supervisor”

`RootlessBwrapRunner` 的假设是 **1 个进程生命周期 = 1 个 Scope = 1 份 Receipt**；而长驻 HTTP MCP Server 打破了这个等式——进程只启动一次，却会持续承载多个 **MCP Session** 与几十上百次 **Tool Call**。

因此 `mareforma-pro` 需要引入**两级生命周期与两级收据模型**：

| 维度 | 0.2.0 `RootlessBwrapRunner`（短任务） | 新增 `MCPProcessSupervisor`（长驻服务） |
| --- | --- | --- |
| **托管对象** | 单次 `bwrap` / 子进程命令 | 长期运行在内部端口的 HTTP MCP Server 进程（或进程池） |
| **采集方式** | 任务结束后离线解析单个 `strace` 日志文件 | 启动时常驻挂载流式管道，按活跃窗口实时路由事件 |
| **边界触发点** | 进程退出即封存 | 入站请求结束签发 **Call 级 Receipt**；Session 关闭/超时汇总签发 **Session 级 Receipt** |
| **角色分工** | 独占整个工具执行期 | 对外监听 `18100` 做透明反向闸门，向内编排固定监听 `18000` 的未改代码 MCP 进程与可选探针 |

---

## 二、四大新增模块的职责与确定性设计方案

整个方案继续坚守 **免 `sudo**` 与 **零置信度猜测** 两条底线——不靠时间窗去猜“哪条事件大概属于哪个请求”，而是靠结构化隔离与 Fail-Closed 对账保证归因确定性。

### 1. 长驻 MCP Process Supervisor（编排与确定性归因中枢）

Supervisor 由 `mareforma-pro` 以普通用户身份启动，对外监听 `18100`，将真正的 MCP Server 进程拉起并托管在本地回环内部端口 `18000`。MCP 客户端需要连接 `18100`，而不是直接连接固定监听 `18000` 的原服务。Supervisor 承担三项核心职责：

* **透明边界识别**：拦截经过 `18100` 的 HTTP/MCP 流量，识别每次 Tool Call 的起止、JSON-RPC 请求 ID、MCP Session 标识（如 `Mcp-Session-Id`）以及上游透传的 `scope_id`。现有的 `MCPApplicationMiddleware` 逻辑可以直接复用或降级为 Supervisor 的“协议解析层”。
* **彻底消灭并发归因歧义（核心难点）**：长驻进程一旦同时处理两个并发请求，进程级 `strace` 看到的 `openat()` 就无法区分归属。Supervisor 提供两档确定性模式：
* **单实例串行闸门 / 多实例 Worker 池（默认推荐）**：对单个底层 MCP 进程强制 `max_concurrency = 1` 串行转发。原服务固定监听 `18000` 时只能使用单 worker；如果服务支持端口参数，可让 Supervisor 拉起 N 个无状态内部进程（例如 `18001..1800N`），每个进程配有独立的采集管道，闸门只把请求路由给当前空闲的进程。这样在任意时刻，**1 个内部进程 = 最多 1 个活跃 `scope_id**`，实现 100% 确定性归因。
* **共享并发诚实降级**：若用户显式关闭串行闸门（例如有状态单实例并发），只要监测到两个 Tool Call 时间窗重叠且未启用协程级运行时隔离，Supervisor 直接对重叠期内的进程级事件标注 **`OPAQUE (concurrent_call_overlap)`**，绝不做启发式猜测。


* **两级收据签发与关联**：单次 MCP 调用响应返回并排空缓冲区后，立刻生成 **Call Receipt**（绑定 `scope_id` 与本次关联到的文件/DB/URL 事件）；当 MCP Session 正常结束或空闲超时，将同一 Session 下的所有 Call Receipt 与跨调用共享状态打包，签发 **Session Receipt**。

---

### 2. 流式 `strace` 进程级采集（解决 `openat()`、临时文件与防绕过审计）

复用 `gpu3` 已验证的免 `sudo` `strace --seccomp-bpf -f -y` 能力，但针对长驻进程做三项关键改造：

* **命名管道（FIFO）流式消费**：不再写入无限膨胀的静态磁盘文件，而是让 `strace` 持续输出到内存管道或带轮转的流，由 Supervisor 内的独立解析线程实时消费并归档到当前激活的 `scope_id` 证据桶中。
* **排空同步屏障（消除尾部漏事件）**：当 HTTP 响应从内部 `18000` 返回并经 Supervisor 对外 `18100` 发回时，最后一条 `openat()` 可能还在 `strace` 管道里排队。Supervisor 在封存本次 Call Receipt 前执行极短的异步排空等待（或向目标进程/管道同步状态），确保当前调用的事件完全落袋后再放行下一个请求。
* **临时文件语义分层（解决第 4 个问题）**：解析器为每个 `scope_id`（及所属 Session）维护一份“已写入的临时路径集合”。
* **本调用内先写后读**的 `/tmp` 文件 → 归入 **`internal_temp_files`**（正常中间产物，透明记录，不误报 `OPAQUE`）。
* **未写先读**的外部已有 `/tmp` 文件 → 严格按 Fail-Closed 标记为 **`OPAQUE (unmapped_tmpfs)`**。


* **全局外联哨兵**：顺带追踪 `connect()` 系统调用，不指望它读出 HTTPS 明文或 SQL 内容，而是拿它当**防绕过对账基线**——一旦发现进程绕开代理直接连了外部 IP，立刻诚实暴露盲区。

---

### 3. 可选 Egress Proxy（解决出站 URL）

作为 Supervisor 可按需开启的用户态子模块，通过给托管的 MCP 子进程注入标准代理环境变量（`HTTP_PROXY`、`HTTPS_PROXY`、`NO_PROXY`）实现零代码接入：

* **分级透明能力（渐进启用）**：
* **基础模式（免证书配置）**：直接记录明文 HTTP 的完整 URL；对 HTTPS 流量通过代理握手阶段（`CONNECT`）确定性记录目标域名与端口，同时标注路径不可见（`https_path_opaque`）。
* **完整 URL 模式（用户态临时 CA）**：Supervisor 启动时在用户目录生成临时自签 CA，通过 `SSL_CERT_FILE`、`REQUESTS_CA_BUNDLE`、`NODE_EXTRA_CA_CERTS` 等环境变量仅注入给受托管的 MCP 子进程（不修改系统证书库、全程免 `sudo`），从而确定性记录完整 HTTPS URL、HTTP 方法与状态码。


* **与 `strace` 交叉对账**：将代理捕获的外联记录与 `strace` 看到的 `connect()` 目标比对。若某语言/库忽略了代理环境变量直连外网，Supervisor 自动附加 **`OPAQUE (egress_proxy_bypassed)`**；若用户选择关闭 Egress Proxy 但 `strace` 监测到外联，则诚实标注 **`egress_uninspected`**。

---

### 4. 可选 SQL / DB Hook（解决数据库查询与连接池盲区）

之所以必须单列此模块，是因为长驻 MCP Server 普遍维护**数据库连接池**——连接早在服务启动时就建好了，单次 Tool Call 执行查询时根本不会触发新的 `connect()`，单靠 `strace` 必然漏抓远程数据库访问。按 MCP Server 的运行环境提供两条可选零代码路线：

* **路线 A：本地数据库透明转发代理（语言无关、零侵入）**
* Supervisor 在本地用户态端口起一个轻量 TCP 转发器，启动 MCP Server 时改写其数据库连接环境变量（如 `DATABASE_URL`、`PGHOST`、`MYSQL_HOST`、`REDIS_URL`）指向本地转发端口。
* 即便底层复用长连接池，只要当前 `scope_id` 期间有数据包穿过该转发通道，Supervisor 就能确定性判定“本次调用访问了哪个数据库实例与逻辑库名”；若走明文内网协议，还可轻量解析查询语句摘要。


* **路线 B：运行时无代码自动插桩（Python / Node.js MCP 首选）**
* 针对 Python MCP，Supervisor 通过启动环境变量注入前置加载器（不改业务代码），自动为常见驱动（SQLite、PostgreSQL、MySQL、SQLAlchemy、DuckDB、Redis 等）挂接观测钩子。
* 优势在于**不受连接池和 TLS 加密影响**，可直接采集精确的数据库名称、操作类型与表/SQL 摘要，且能借助协程上下文在并发场景下精准绑定 `scope_id`。


* **本地嵌入式库兜底**：SQLite、DuckDB 等文件型数据库天然会被第 2 部分的 `strace` `openat()` 捕获，可与 DB Hook 互相印证。若用户既未开代理也未开 Hook，则远端库流量诚实标记为 **`db_uninspected`**。

## 三、端到端事件关联与收据签发闭环

将四块能力拼合后，单次 MCP Session 与调用的完整数据流转分为 **5 个阶段**：

1. **托管启动**：`mareforma-pro` 的 Supervisor 启动并监听 `18100`；按用户配置拉起固定监听 `18000` 的内部 MCP Server（外包 `strace` FIFO）、可选 Egress Proxy 与可选 DB Hook/代理。
2. **请求入站与槽位绑定**：Agent 向 `18100` 发起 MCP Tool Call；Supervisor 解析 `session_id` 与 `scope_id`，分配并锁定一个空闲的内部 MCP 进程槽位，通知路由表进入激活状态。
3. **多通道并行取证**：MCP 进程正常处理业务；协议层元数据（原 `MCPApplicationMiddleware` 能力）、`strace` 文件与 `connect` 流、Egress Proxy URL 流、DB Hook 查询流全部实时写入该 `scope_id` 的独立证据桶。
4. **调用结束与 Call Receipt 签发**：MCP 响应返回后，Supervisor 触发短排空屏障，执行三项确定性对账（临时文件先写后读区分、`connect` 与 Proxy 防绕过对账、并发重叠检测），签发带 HMAC 签名的 **Call Receipt**，随后解锁槽位放行下一请求。
5. **会话结束与 Session Receipt 封存**：MCP Session 关闭或超时后，Supervisor 汇总该 Session 下的全部 Call Receipt 形成 **Session Receipt**，异步转换为 OpenTelemetry 的 `ProcessSpan` 与 `Span Link` 导出。

## 四、对 `mareforma-pro` 的架构收口建议（向后兼容 0.2.0）

* **保持严格模块化与渐进开关**：把 `MCPProcessSupervisor` 作为与 `RootlessBwrapRunner` 并列的新运行器，`strace` 为默认采集底座，Egress Proxy 和 DB Hook 均设计为显式开关项（关闭时零开销，且触发对应观测盲区时走统一 Fail-Closed 诊断码，绝不伪造结论）。
* **统一收据 Schema 扩展**：在 0.2.0 现有的 `observed_files` 与 `opaque_reasons` 基础上，为收据增量补充 3 个可选列表字段——`internal_temp_files`（自写自读临时文件）、`observed_egress_urls`（出站 URL/域名）与 `observed_db_queries`（访问的数据库与操作摘要），让下游 `assert_claim()` 与 OTel 导出器无缝消费。

### 3. 五阶段生命周期闭环

1. **阶段 1：启动托管**
Supervisor 拉起内部固定监听 `18000` 的 MCP 进程、挂载 `strace` FIFO 管道，按开关初始化 Egress Proxy 与 DB Hook，并对外监听 `18100`。
2. **阶段 2：入站锁定**
Agent 请求抵达 `18100`；Supervisor 提取 `session_id` 与 `scope_id`，锁定空闲的内部 MCP 槽位，将流式事件路由表切换至当前 `scope_id`。
3. **阶段 3：多路取证**
MCP 进程正常处理业务；`strace` 实时采集 `openat`/`/tmp`/`connect`，已开启的 Egress Proxy 与 DB Hook 同步向当前 `scope_id` 证据桶写入出站 URL 与数据库记录。
4. **阶段 4：排空签 `CallReceipt**`
MCP 响应返回后，Supervisor 触发流式排空屏障（Drain Barrier），完成 `/tmp` 先写后读区分与代理防绕过对账，签发 Call 级 HMAC 收据并解锁槽位。
5. **阶段 5：封存 `SessionReceipt**`
MCP Session 关闭或空闲超时后，Supervisor 汇总该 Session 下的全部 `CallReceipt` 签发 Session 级收据，并异步转换为 OpenTelemetry `ProcessSpan` 与 `Span Link` 导出。

### 4. 可选模块开关与 Fail-Closed 降级矩阵

| 可选模块 | 开启状态（`ON`） | 关闭状态（`OFF`） | 异常 / 绕过时的 Fail-Closed 降级 |
| --- | --- | --- | --- |
| **Egress Proxy** | 记录 `observed_egress_urls`（免证书模式记录域名端口并标 `https_path_opaque`；临时 CA 模式记录完整 URL） | 出站 URL 通道关闭；若 `strace connect()` 监测到外联，诚实标注 `egress_uninspected` | 开启代理但 `strace connect()` 发现直连外网 IP → 标 `OPAQUE(egress_proxy_bypassed)` |
| **SQL / DB Hook** | 穿透连接池记录 `observed_db_queries`（本地 TCP 转发代理或 Python `sitecustomize` 自动插桩） | 远程 DB 通道关闭，保留本地 SQLite/DuckDB 的 `openat` 捕获；远端库流量标注 `db_uninspected` | 未配置对应驱动或转发环境变量且监测到未知外联 → 诚实记为盲区 |
| **串行闸门 / Worker 池** | 严格 `1 内部进程 = 1 活跃 scope_id`，100% 确定性归因 | 允许同进程并发处理多请求 | 一旦监测到两请求时间窗重叠 → 强制标 `OPAQUE(concurrent_call_overlap)` |
